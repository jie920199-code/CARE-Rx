# 架构建议

## 1. 设计结论

建议首版采用局域网内的模块化单体：一台受控 Windows 主机运行 Next.js + TypeScript 服务，电脑、平板和手机仅通过浏览器访问。SQLite 只保存用户、权限、经批准的内容版本和最低限度安全审计，不保存患者评估输入；患者输入使用有过期时间的服务端会话内存。为后续 PostgreSQL 和持久化临床记录留出仓储边界。

## 2. 建议分层

```text
UI / 角色化视图
  -> 应用服务（工作流、权限、审核确认与导出）
    -> 安全门 + 确定性规则引擎
      -> 领域模型（临时评估、候选处方、内容版本、非患者审计）
        -> 临时患者会话（内存，超时清除）
        -> Prisma 仓储 -> SQLite（账号、配置、内容版本、非患者审计）

clinical-data/（版本化评估定义、处方、规则）
  -> Schema 校验 -> 临床审批 -> 发布包 -> 规则运行时
```

- `clinical-data` 是源内容，页面不得复制临床阈值。
- 规则引擎仅接受校验后的事实和白名单操作符，输出候选、排除项和可解释理由。
- 护工版/宣教版来自处方定义中经批准的角色化内容字段；不是由大模型临时改写。
- 导出时生成带版本元数据的不可变文件；系统在无留存模式下不保存患者级历史快照。

## 3. 建议目录

```text
clinical-data/
  assessments/ prescriptions/ decision-rules/ schemas/
```

## 4. 关键非功能要求

- 响应式但以治疗师电脑工作流优先；护工手机界面突出步骤、剂量、辅助、终止标准和记录入口。
- 身份与权限采用最小权限；导出前需要治疗师再次确认并把身份写入导出元数据。
- 局域网部署需固定主机地址、仅内网防火墙规则、HTTPS 或机构批准的等效保护、健康检查和离线运行说明。
- 患者会话设绝对超时和空闲超时；退出、超时、服务器重启或成功导出后清除。日志只记录非患者技术事件。
- 可观测性不得泄露身份数据；规则执行保留结构化理由和内容哈希。

## 5. 已识别技术风险

- Next.js 服务进程、Windows 自启动/升级、局域网证书和主机防火墙需要专项验证。
- 多终端只能通过应用服务访问；SQLite 文件不得作为网络共享。轻量账号/配置可由单服务进程使用 SQLite，患者记录扩展启用前应重新评估 PostgreSQL。
- Prisma 对 SQLite/PostgreSQL 的类型与约束差异需通过仓储测试和迁移演练控制。
- 网页登录、会话劫持防护、跨站请求防护、登录限速和治疗师确认身份不能推迟到试点后处理。
